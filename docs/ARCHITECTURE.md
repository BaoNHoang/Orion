# Orion Architecture

## Purpose

Orion is a local-first, single-user personal assistant. The first deployment is a Windows-hosted progressive web application. It prioritizes local data ownership, explicit memory consent, visible web sources, and permission-gated future tools.

This document describes what is implemented today, why it is structured this way, and the boundaries that should guide future work.

## System map

```text
Browser PWA
  React interface, voice controls, conversation queue, 3D presence
        |
        | HTTP on 127.0.0.1:8787
        v
Local Node service
  API routing, SQLite persistence, research, prompts, cancellation
        |
        | HTTP on 127.0.0.1:11434
        v
Ollama
  qwen3:4b local language model
```

The browser is the user experience. The Node service is the application brain around the model: it decides what context to include, persists data, retrieves web evidence, and enforces the current privacy rules. Ollama generates language; it does not own Orion's memory, tools, or user interface.

`server.mjs` intentionally began as one file to make the local MVP easy to run. It is now the main technical-debt boundary: future feature work should move behaviour out of it by responsibility, not by arbitrary file size.

## Data model

SQLite is the source of truth for the first single-user build.

| Table | What it stores | Current use |
| --- | --- | --- |
| `conversations` | Chat title, workspace, created time | Sidebar and conversation loading. |
| `messages` | User and Orion messages | Transcript and short recent-history context. |
| `memories` | Explicitly approved personal details | Up to eight approved items are included in an ordinary chat prompt. |
| `workspaces` | User-created context categories | Conversation organization. |
| `research_reports` | Search query and retrieved source evidence | Visible citations and research continuity on refresh. |
| `council_reports` | Astrium positions and final conclusion | Council panel continuity on refresh. |

Important: current memory is curated key-value context, not semantic memory. Orion does not yet embed, rank, or retrieve facts from every old conversation. Old transcripts remain in SQLite, but they are not automatically summarized into durable knowledge.

## Ordinary chat flow

```text
User message
  -> UI queues a turn
  -> /api/route decides whether research or Astrium is relevant
  -> approved memories + recent chat history are selected
  -> optional /api/research retrieves web evidence
  -> /api/chat builds Orion's system prompt and calls Ollama
  -> NDJSON response streams tokens to UI and speech
  -> final response is persisted in SQLite
```

The model receives a system prompt, recent messages, approved memory, and optional source evidence. This is context construction. The model itself is not permanently learning from the conversation.

Ordinary requests use a bounded output budget and disable reasoning for lower latency. Requests for concrete rankings get additional response validation to reduce incomplete lists and refusals.

## Research flow

Research is triggered by freshness-sensitive requests, explicit search language, or selected ranking questions.

```text
Query cleanup
  -> DuckDuckGo and Bing search in parallel
  -> deduplicate result URLs
  -> fetch public pages with SSRF checks
  -> extract and rank relevant passages
  -> store report and show sources
  -> provide selected evidence to Orion or Astrium
```

Research evidence is untrusted input. Prompts explicitly instruct the model to ignore instructions found inside web pages. The current system provides source visibility but does not yet verify every generated sentence against a citation.

## Astrium council flow

Astrium is Orion's advisory presentation layer.

```text
Complex or explicitly requested topic
  -> generate four role-specific positions as structured JSON
  -> validate completeness and repair malformed output once
  -> synthesize Orion's concise decision
  -> persist positions and conclusion
```

Nebula, Helix, Nereid, and Nova have different prompt instructions. Today they are generated by the same local model inside efficient batched calls. This is role-based deliberation, not four independently hosted agents with separate tool access or private long-term state.

That distinction matters: independent agents cost more time and tokens. Orion should only evolve Astrium into separate calls when evaluations show that the additional disagreement improves decisions.

## Voice flow

```text
Microphone
  -> browser SpeechRecognition
  -> transcript enters the same turn queue as typed text
  -> Ollama text response
  -> browser SpeechSynthesis reads response aloud
```

The visual audio meter uses `getUserMedia` locally. Browser speech recognition is not local speech-to-text and normally needs internet access. Speech synthesis uses installed browser or Windows voices and can often work offline.

### Barge-in and interruption

When a finalized voice transcript arrives while Orion is speaking or processing:

1. Orion stops speech playback.
2. The browser aborts the active route, research, chat, or Astrium HTTP request.
3. The Node service propagates cancellation to Ollama.
4. Partial assistant output is discarded.
5. A clarification is combined with the original request; a new topic supersedes it.

The echo filter rejects likely playback transcriptions while allowing direct commands such as `stop`, `wait`, `no`, and `actually`.

## Privacy and security boundary

Current protections:

- Orion binds its application service to `127.0.0.1`.
- Conversation data stays in a local SQLite file.
- Sensitive memories require an explicit save action and can be deleted.
- Audio recordings are not persisted.
- Web research is visible in the UI.
- Public-page fetching rejects private-network targets.

Current limits:

- SQLite data is not encrypted at rest by Orion.
- The local API has no user authentication because the MVP assumes one Windows user on one machine.
- There is no tool-execution framework yet, so there is no audited permission system for files, applications, calendars, or email.
- The web app currently permits broad local CORS for development convenience.

Before adding file access or sync, introduce a capability-based tool layer: every tool declares its scope, asks for consent, records an audit event, and receives only the minimum data needed to perform the action.

## What is not RAG yet

RAG means retrieval-augmented generation: before asking the model, the system searches a knowledge store for relevant chunks and adds them as context.

Orion has web retrieval, but it does not yet have personal-document RAG. The missing pieces are:

1. A document ingestion pipeline with user approval.
2. Chunking and metadata.
3. Embeddings and a local vector index.
4. Retrieval and reranking for each request.
5. Citations from Orion's answer back to local documents.
6. Deletion, expiry, and workspace-scoped access rules.

RAG will improve grounding in your documents and past work. It will not make a small local model equivalent to a frontier model; model capability, tools, voice, and evaluation remain separate concerns.

## Modularization plan

Do not split `server.mjs` mechanically. Extract modules as the next related feature requires them.

```text
server.mjs                         Composition root and HTTP startup
server/database/                   Schema, queries, migrations, backup
server/chat/                       Prompt building, history, stream handling
server/models/                     Ollama and future provider adapters
server/research/                   Search providers, page safety, extraction, ranking
server/astrium/                    Routing, role definitions, structured deliberation
server/memory/                     Consent, memory policy, future retrieval
server/tools/                      Permissioned file, reminder, and OS capabilities
server/voice/                      Local STT integration and voice-session policy
```

The first extraction should be `server/models/ollama.mjs` and `server/chat/streaming.mjs`, because cancellation and model routing are now shared concerns. The second should be `server/research/`, which is already a cohesive subsystem. Database access should move only when migrations or backups are added.

## Path to a stronger assistant

1. Local Whisper plus voice activity detection for offline speech and dependable interruption.
2. Semantic workspace memory and document RAG with explicit ingestion consent.
3. Permissioned tools and a local audit log.
4. Model routing: small local model for simple work, stronger local or cloud provider for difficult work.
5. Evaluation scenarios for research accuracy, interruption, memory consent, and tool safety.
6. Encrypted backup and sync only after the single-device experience is reliable.

## Comparison boundary

ChatGPT's internal implementation is not public, so Orion should not claim to reproduce it. Public OpenAI documentation shows examples of the kind of product infrastructure that separates a basic chat application from a mature assistant: stateful conversations and tool orchestration in the Responses API, and low-latency voice-to-voice sessions in the Realtime API.

- [Responses API overview](https://developers.openai.com/tracks/building-agents#building-with-the-responses-api)
- [Realtime audio conversations](https://developers.openai.com/api/docs/guides/realtime-conversations#audio-inputs-and-outputs)
